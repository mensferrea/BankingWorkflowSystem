# Автоматизированная система обработки банковских заявок

Промышленное веб-приложение для автоматизации первичного приема, скоринга, андеррайтинга и жизненного цикла кредитных заявок клиентов банка.

---

## 1. Концепция и решаемые бизнес-задачи

В классических банковских процессах согласование кредита проходит через несколько обособленных подразделений:
1. **Фронт-офис (Оператор):** регистрация физического лица, ввод параметров кредитного продукта, прикрепление сканов документов (паспорт, 2-НДФЛ, договор).
2. **Андеррайтинг и кредитный комитет (Менеджер):** расчет кредитной нагрузки (ПДН/DTI), проверка скорингового рейтинга, утверждение условий или отказ с обязательным обоснованием.
3. **Бэк-офис и аудит (Администратор/Менеджер):** формирование юридического комплекта (кредитный договор в формате Word по шаблону, протокол решения), выгрузка реестров в Excel для отчетности перед регулятором, контроль журнала действий сотрудников.

Система автоматизирует всю сквозную цепочку и исключает несанкционированные переходы статусов.

## 2. Архитектура решения

Проект построен по принципам **Clean Architecture** (чистая архитектура) и предметно-ориентированного проектирования (DDD):

```
BankingWorkflowSystem/
├── src/
│   ├── BankingWorkflow.Domain/          # Чистые бизнес-сущности, Enum-типы, бизнес-правила и Domain Exceptions
│   ├── BankingWorkflow.Application/     # DTO, интерфейсы сервисов, валидаторы FluentValidation
│   ├── BankingWorkflow.Infrastructure/  # EF Core, PostgreSQL, ASP.NET Identity, ClosedXML, OpenXML, файловое хранилище
│   └── BankingWorkflow.Web/             # Единый хост: ASP.NET Core Web API (JWT) + Swagger + Blazor Interactive Server
├── tests/
│   └── BankingWorkflow.Tests/           # Автоматические тесты (xUnit) для логики статусов, формул аннуитета и валидаторов
├── docker-compose.yml                   # Запуск PostgreSQL и приложения в Docker
└── Dockerfile                           # Multi-stage сборка .NET 10
```

### Почему именно такое разделение?

* **`BankingWorkflow.Domain`** не зависит ни от каких внешних пакетов, баз данных или UI. Сущность `Application` самостоятельно инкапсулирует строгий конечный автомат (`NEW` → `IN_PROGRESS` → `APPROVED` / `REJECTED`) и математику расчета аннуитетного платежа и переплаты.
* **`BankingWorkflow.Application`** отделяет входные и выходные контракты (DTO) от модели БД, предотвращая утечку внутренних данных. Валидация выполняется через `FluentValidation`.
* **`BankingWorkflow.Infrastructure`** реализует всю работу со сторонними библиотеками и БД (PostgreSQL, ClosedXML, OpenXML). При необходимости хранилище или драйвер базы данных можно заменить без модификации бизнес-логики.
* **`BankingWorkflow.Web`** объединяет в одном хосте REST API контроллеры для интеграций и интерактивный Blazor UI с серверным рендерингом (`InteractiveServer`).

## 4. Бизнес-логика жизненного цикла заявки

Статусы заявки подчиняются строгому конечному автомату:

```
[ NEW ]  ──(Взятие в работу: Оператор/Менеджер)──>  [ IN_PROGRESS ]
                                                          │
                   ┌──────────────────────────────────────┴──────────────────────────────────────┐
                   │                                                                             │
(Одобрение: Менеджер/Админ + комментарий)                       (Отказ: Менеджер/Админ + комментарий)
                   ▼                                                                             ▼
            [ APPROVED ]                                                                  [ REJECTED ]
          (Финальный статус)                                                            (Финальный статус)
```

1. **`NEW` (Новая):** первичная регистрация заявки оператором. На этом этапе доступны редактирование параметров займа и прикрепление документов.
2. **`IN_PROGRESS` (В обработке):** заявка передана андеррайтерам. Параметры займа блокируются от случайных изменений.
3. **`APPROVED` (Одобрена):** кредитный комитет принял положительное решение. Доступна выгрузка официального кредитного договора в формате Word.
4. **`REJECTED` (Отклонена):** отказ по результатам оценки рисков или скоринга с обязательным указанием причины в журнале.

Оператор **не имеет права** переводить заявку в `APPROVED` или `REJECTED` — это действие аппаратно защищено ролью `Manager` и `Admin`.

## 6. Запуск и развертывание

### Вариант 1: Запуск через Docker Compose (рекомендуется)

1. Убедитесь, что Docker запущен.
2. Выполните команду в корне проекта:
   ```bash
   docker compose up -d
   ```
3. Откройте в браузере:
   * Веб-интерфейс: `http://localhost:5000`
   * Swagger REST API: `http://localhost:5000/swagger`

### Вариант 2: Локальный запуск из исходного кода

1. Убедитесь, что запущен PostgreSQL на порту 5432 (или запустите только БД через `docker compose up -d postgres`).
2. Примените миграции (выполняются автоматически при запуске приложения или вручную):
   ```bash
   dotnet ef database update --project src/BankingWorkflow.Infrastructure --startup-project src/BankingWorkflow.Web
   ```
3. Запустите веб-проект:
   ```bash
   dotnet run --project src/BankingWorkflow.Web
   ```
4. Приложение станет доступно по адресу из `Properties/launchSettings.json`.

## 7. Модули системы

### 1. Интерактивный Дашборд (`/`)
* Метрики портфеля: общее число заявок, новые, в работе, одобренные, отклоненные.
* Сумма одобренного кредитного объема и общий запрашиваемый объем.
* Процент одобрений (конверсия скоринга).
* Прогресс-бар структуры статусов портфеля.
* Таблица недавних заявок с быстрыми ссылками.

### 2. Реестр кредитных заявок (`/applications`)
* Полнотекстовый поиск по номеру заявки, ФИО заемщика, ИНН.
* Фильтрация по статусам (`New`, `InProgress`, `Approved`, `Rejected`), продуктам, суммам и датам.
* Сортировка по дате, сумме, клиенту, номеру.
* Экспорт отфильтрованного реестра в стилизованный файл Excel (ClosedXML).

### 3. Карточка кредитной заявки (`/applications/{id}`)
* Полная сводка финансовых параметров: сумма, срок, ставка, ежемесячный аннуитетный платеж, общая сумма к выплате, переплата.
* Блок данных заемщика с переходом в картотеку.
* Кнопки управления жизненным циклом с модальным окном подтверждения и обязательного обоснования решения.
* Прикрепление, скачивание и удаление документов (паспорт, 2-НДФЛ, договор, залог).
* Формирование кредитного договора по банковскому шаблону в `.docx` (OpenXML).
* Формирование выписки из решения кредитного комитета в `.docx` (OpenXML).
* Хронологическая лента (таймлайн) всех изменений статуса с фиксацией даты, автора и комментария.

### 4. Картотека клиентов (`/clients` и `/clients/{id}`)
* Реестр заемщиков с поиском по реквизитам.
* Карточка клиента с отображением персональных данных, документов, дохода, трудоустройства и скорингового рейтинга.
* История всех когда-либо поданных этим клиентом заявок.
* Форма регистрации нового клиента с валидацией (совершеннолетие 18+, корректность паспорта и ИНН).

### 5. Журнал аудита (`/audit-logs`)
* Доступен менеджерам и администраторам.
* Хранит хронологию всех действий: создание заявок, изменение анкет клиентов, смена статусов, загрузка файлов, авторизация.
* Фильтрация по типу сущности, событию и тексту.

### 6. Центр уведомлений
* Колокольчик в верхней панели с индикатором количества непрочитанных событий.
* Автоматическая генерация системных уведомлений при поступлении новых заявок и смене статусов.
* Возможность перехода напрямую к заявке из выпадающего списка и отметка о прочтении.

### 7. REST API & Swagger UI (`/swagger`)
* Контроллеры `AuthController`, `ApplicationsController`, `ClientsController`, `DocumentsController`, `ReportsController`, `DashboardController`, `AuditLogsController`, `NotificationsController`.
* Поддержка авторизации по JWT-токену (кнопка `Authorize` в Swagger UI).

```bash
dotnet test
```
